THE FIELD GUIDE

A workspace that works.

Real guests need a real engine. Here’s how to get from a fresh Codespace to your first instance.

01 / Start in Codespaces

Use a Debian/Ubuntu-based Codespace. The installer attempts userspace packages with apt if you have sudo; the panel itself never needs root. An unavailable package or accelerator is reported, not hidden.

bash install.sh

Open the Ports tab, forward 31120, and keep visibility Private. New Codespaces forwards are Private by default; verify existing port visibility yourself. Set SKVM_COOKIE_SECURE=1 in .env for HTTPS forwarding.

The Python virtual environment is used automatically. SQLite initializes on startup at database/skvm.db. Workspace data lives in data/; neither is committed to Git.

02 / First administrator login

On a new empty panel, sign in with username admin and initial password admin123. Login opens Overview and all authorized pages and controls are available immediately. A non-blocking reminder asks you to set a private password of 12–128 characters in Profile. Keep the forwarded port Private. Existing accounts are never reset, replaced or silently promoted.

To opt out, set SKVM_BOOTSTRAP_ADMIN=0 before first startup and create an administrator with a hidden terminal password prompt:

python skvm.py create-admin --email you@example.com

The root installer installs Node and Python dependencies, builds frontend assets, initializes safely and starts Gunicorn on port 31120. Use --background for background hosting or --no-start for setup only. No systemd or privileged Docker daemon is required. Registration creates ordinary users.

03 / Verify the environment

bash scripts/check-environment.sh
python skvm.py verify-images
python scripts/qemu-smoke-test.py

The QEMU smoke test starts a temporary, diskless, paused machine under TCG and tears down only that exact process. It does not create a VPS or boot an OS. A passing accelerator probe does not prove that a particular cloud image boots.

QEMU requires qemu-system-x86_64, qemu-img, and cloud-localds. It uses TCG by default. KVM is used only with explicit SKVM_USE_KVM=1, read/write access, and a passing live KVM probe. Missing local capabilities can be replaced by an external node.

04 / Provision a real instance

Create VPS → select QEMU or Docker → choose OS, allocations, and node → review → confirm. Downloads happen in a persistent background job. Only a successfully created disk and seed, or real Docker container, becomes a VPS record. New instances are stopped; use Start to launch.

QEMU images are checked via allowlisted HTTPS before download, validated with qemu-img, and copied into independent QCOW2 disks. Admins can pin trusted SHA256 hashes. Old Fedora 40 and Debian 11 images carry lifecycle warnings; availability is not promised.

SSH & console access

QEMU forwards SSH to 127.0.0.1:<assigned-port> on the provisioning host. The details page shows the actual port and username. No public IP or password is fabricated. From a Codespace terminal, run the shown SSH command directly.

From your own computer, first create a real SSH tunnel to the Codespace using GitHub CLI:

gh codespace ssh -c YOUR_CODESPACE -- -L 2222:127.0.0.1:22000
# In another local terminal, using the real assigned guest username:
ssh -p 2222 ubuntu@127.0.0.1

Replace 22000 with the VM’s assigned port. For an external node, tunnel through that Linux node instead. Codespaces’ browser HTTP proxy cannot carry raw SSH.

The QEMU console relays guest serial input through a Unix socket and reads actual serial logs. Docker console offers logs and fixed in-container diagnostic commands, not an unrestricted host shell. Base OS containers have no automatically installed SSH daemon.

Guest networking is restricted by default. QEMU uses user-mode networking without bridge/TAP privileges; Docker uses an internal bridge. The host firewall and external infrastructure still need operator security review.

Docker setup & storage limits

The panel uses the Python Docker SDK, not CLI shell commands. It must have access to a local Unix daemon, preferably rootless (for example DOCKER_HOST=unix:///run/user/1000/docker.sock). Direct TCP/SSH Docker transports are refused, even with TLS: deploy the authenticated SKVM agent beside the daemon so capacities come from the correct host. A socket is never mounted inside guest containers or exposed as a browser API.

Do not create a privileged Docker-in-Docker container just to make this panel work. If the Codespace’s daemon is unavailable or disallows resource controls, use an external node. Docker capabilities are validated by daemon ping and info; creation errors are shown by the real SDK.

Memory and CPU constraints are applied at container creation. Hard rootfs storage quotas require a verified compatible driver configuration (for overlay2, typically XFS with project quotas). Only after checking it, set SKVM_DOCKER_STORAGE_LIMITS=1. Otherwise users must explicitly accept a budget-only disk allocation. The dashboard always labels enforcement correctly.

External Linux provisioning nodes

The panel can stay in Codespaces while an authenticated HTTPS agent creates real QEMU VMs or Docker containers elsewhere. Check out this same source on a Linux node, install userspace dependencies, and use a separate persistent data directory.

bash scripts/install.sh
# Put a newly generated random token in the node’s private .env:
python -c 'import secrets; print(secrets.token_urlsafe(48))'
# SKVM_NODE_TOKEN=<generated value>
python node_agent.py

The agent listens only on loopback 127.0.0.1:5556. Put it behind your HTTPS reverse proxy on port 443 with a valid certificate and firewall access to the panel. See docs/external-nodes.md for an nginx example and deployment precautions. Do not forward port 5556 publicly or use self-signed TLS without a properly configured trust chain.

On the panel, add the exact DNS host to SKVM_NODE_HOSTS and restart. Then Admin control → External nodes → enter its HTTPS origin and matching token. Tokens are stored encrypted. Connection is verified before registration. Panel and agent use protocol version 1; upgrade them together. Certificate verification is never disabled.

The agent reports effective host RAM/CPU/storage, actual guests and containers, image configuration, and provisioning state. All mutations use persistent idempotent operation IDs. An unreachable node is “unknown”, never “stopped” or “successful”. Long-running operations can be reconciled without replaying destructive actions.

Resource & persistence notes

Allocations are virtual configuration, not additional physical hardware. The node enforces a conservative RAM ceiling, no CPU overcommit, full-disk storage reservations, user quotas, and a maximum instance count. Capacity follows actual cgroup membership and ancestor ceilings/headroom; unavailable capacity blocks new allocations with a reason. Usage scope is labeled separately. TCG is slow for CPU-heavy work. Cloud-init readiness is not inferred just because the QEMU process is running.

Codespace shutdown stops processes but retains workspace files; deletion of a Codespace can delete its disks and SQLite database. Back up the database, both private key files, and stopped guest storage together. The panel is intended for trusted personal/team workspaces, not untrusted public hosting.

Tests that don’t pretend

.venv/bin/python -m pytest -q
SKVM_TEST_MODE=1 python skvm.py

Unit tests use temporary databases and explicitly mocked OS boundaries. Test mode refuses all provisioning and lifecycle mutations. No test/demo guests appear in your live database. A real local HTTPS test validates CA/hostname checks and bearer rejection, not external-node deployment. Full OS/cloud-init/SSH and Docker acceptance tests require explicit opt-in on an equipped host; see docs/testing.md for commands and trusted checksum requirements. Reconciliation inspects actual resources without repeating destructive actions; ambiguous evidence retains reservations. See README for covered checks, known boundaries, and crash recovery commands.
